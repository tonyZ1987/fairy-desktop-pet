## 2. 怎么用

**启动**：双击 **`restart_fairy.vbs`**（推荐）或 `start_fairy.vbs`。
（**别用 python 直接跑**，会弹黑框；也别让我启动 —— AI 起的进程会被沙箱连带回收。）

**看不见宠物 / 怀疑它没起来**：双击 **`check_fairy.vbs`**，会弹窗给出结论。

| 操作 | 结果 |
|---|---|
| 左键拖 | 移动（松手记住位置） |
| **右键** | 开/关自绘菜单（8 秒无操作且鼠标移开会自动收起） |
| 双击 | 冒一句话（照官方语态写的，短句、不喊口号） |
| 菜单 →「**尺寸**」滑块 | 三档：小 200 / 中 260 / 大 320 px，右侧标实际像素（缓存已烘好，秒切） |
| 菜单 →「**模式**」滑块 | 自动 / 手动 |
| 菜单 →「**状态**」滑块 | **切到手动时才出现**：常态 / 工作态 |
| 菜单 →「**自动**」滑块 | **自动时才出现**：跟随 WorkBuddy / **60 秒循环**（演示：自己来回切，方便看动效） |
| 菜单 →「归位」 | 回到右下角（找不到它时用这个） |
| 菜单 →「退出 fairy」 | 退出 |
| 放个 `stop.txt` | 也会退出（不用碰鼠标） |
| **再双击一次启动器** | 它会把窗口归位并亮出来（多实例不会叠出两只） |

**滑块是"点击 + 拖动"两用的**：点一下即选中；也可以按住不放左右拖，
经过段间那 2 px 缝隙时不会失灵（缝隙的命中被算进左段）。
菜单宽度按**两种模式里更宽的那一行**算死 ⇒ 切自动/手动时不会横向跳动。
预览图见 `STEP12_菜单_滑块式.png`（四种状态各一张）。

**★ 任务完成通知（2026-09-22 新增，这是做 fairy 的初衷）**

我（fairy）干完活时写一个 `notify.json`，桌宠每 0.5 秒看一眼，读到就弹一张**通知卡**：

```
┌────────────────────────────────────┐
│ ● fairy                            │
│ 主人，湖州西凤漾商业策划方案文本    │
│ 已完成，请前往查阅。                │
└────────────────────────────────────┘
```

- 卡片**自动折行**（最多 3 行），停留 **12 秒**后淡出（淡入 0.25 s / 淡出 0.5 s）
- **消费即删**：桌宠读完就把 `notify.json` 删掉 ⇒ 通知是一次性的，重启不会重弹
- **不碰网络、不碰别的程序**：没有账号、没有权限、没有服务；桌宠没开也不会报错（只是没人读）
- **原子写**（先写 `.tmp` 再替换）⇒ 不会出现"桌宠正好读到半个文件、那一轮通知丢了"

你自己想试：双击 **`test_notify.vbs`**（桌宠没开的话先双击 `restart_fairy.vbs`）。
自己发一条：`python fairy_notify.py "你的话"`，另有 `--done`（同时收工，眼睛睁开）、
`--work`（同时开工，半睁眼）、`--secs 20`（卡片多停一会儿）。
样式预览见 `STEP13_任务完成通知.png`。

以后我干完活会**自己**发，你不用做任何操作。

**想临时看一眼再退出**：`python fairy_pet.py --smoke 6`（显示 6 秒后自退，会弹黑框，仅排障用）。
`--hidden` 只建窗口不显示（自检/测试用，屏幕上不会出现任何东西）。

## 3. 两个状态与触发机制

| 状态 | 形象 | 对应官方 |
|---|---|---|
| `idle` | 睁眼 | `normal` |
| `working` | **半睁眼**（眼睑落到 86，向下浮动 2.0 / 向上 0.9） | `thinking` |

**状态来源，优先级从高到低：**

1. **右键菜单手动指定**（滑块切到"手动"后，由「状态」滑块决定）
2. **本目录 `state.json`** —— 我每次开工写 `working`、收工写 `idle`：

```json
{ "state": "working", "ts": "2026-09-21T18:00:00", "ttl": 2700, "note": "任务开始" }
```

- `state`：`working` / `idle`（也认 `thinking` / `busy` / `normal` 等同义词）
- `ttl`：**兜底超时**（秒）。文件超过这么久没更新 ⇒ 自动回落到 `idle`，防止我忘了写导致一直半睁。不写则用程序里的 `AUTO_TIMEOUT_S`（默认 2700 s = 45 min）
3. 都没有 ⇒ `idle`

**★ 「60 秒循环」（2026-09-22 新增，菜单「自动」滑块的第二档）**：
不读 `state.json`，直接每 60 s 在常态 ↔ 工作态之间自己来回切 —— 演示、录屏、给人看动效用。
切回"跟随 WorkBuddy"就恢复读 `state.json`。

**切换不是硬切**：睁 → 半睁 **0.70 s**（眼睑连续下落），半睁 → 睁 **0.55 s**（抬起略快），都是 smoothstep。
（官方是硬切；这一处是我们主动的柔和化，见 STEP2 §2.5。）

**状态机已实测四个场景**（无窗口离线跑）：

| 场景 | 结果 |
|---|---|
| `state.json` 写 working | `open_t` → 0.000（半睁）✅ |
| working 但 ttl 已过 | 自动回落 idle，`open_t` 平滑升到 1.000 ✅ |
| 手动 working（关跟随） | 无视 state.json，保持 0.000 ✅ |
| 重新跟随 + idle | 回到 1.000 ✅ |

## 4. 实时化：为什么能上 60 fps

参考渲染器 **0.45 s/帧**，离 60fps 差 27 倍。主程序走的是另一条路：

### 三条洞察

1. **静态层**（外发光 + 外盘渐变 + 白描边）永不变化
   ⇒ 预烘焙成一张「黑底观感」的图，运行时一次 `paste`（无遮罩＝memcpy，**0.01 ms**）。

2. **眼睛各层只是同心圆的半径缩放**，而缩放系数只随呼吸相位变化
   ⇒ 预烘焙 **90 个相位帧**（1.5 s × 60 fps），运行时按下标取用，零重算。

3. **眼睑遮罩可以解析求值**。官方 clipPath 是二次贝塞尔，在 `mid`（弧中点）这个自由度上能
   **拆成两个与 mid 无关的基函数**：

   ```
   cy(t) = A·g(t) + B·h(t)     g(t)=(1-t)²+t²      h(t)=2t(1-t)      A=mid−sag/2, B=mid+sag/2
   ```

   G、H 预计算成一维数组，每帧只算 `ycurve = A·G + B·H` —— 不再逐帧跑 3001 点插值（**0.10 ms**）。

### 还有一条关键设计（省掉一次除法、也省掉一次通道翻转）

最终 alpha 里含 `max(R,G,B)/255`，而 `UpdateLayeredWindow` 要的是**预乘 BGRA**；
预乘后正好等于「黑底观感」本身（`rgb×alpha = color`）。所以：

> **整条链只在黑底上合成，最后补一个 alpha 通道即可。**

既然如此，就让画布**直接以 BGR 存放**，「转 BGRA」退化成一次连续内存拷贝 + 一次 max。
实测这一步从 **1.72 ms 降到 ~0.7 ms**。（代价：自绘 UI 的颜色要过一层 `bgr()` 翻转，见 `fairy_layers.py`。）

### ★ 但 alpha 不能只靠 `max(R,G,B)`（2026-09-21 被主人截图抓到）

`max(R,G,B)` 成立的前提是**对象都是"黑底上的亮物"**（发光、白环、虹膜都对）。
可一旦出现**深色不透明块**，它就彻底失效：

| 部位 | 最大通道 | 只靠 max(RGB) 得到的 alpha | 在浅色桌面上的后果 |
|---|---|---|---|
| 深色睫毛环 `#2b3388` | 136 | **0.53** | 被冲淡成亮蓝 |
| **菜单面板 `#12141c`** | 28 | **0.11** | **整片惨白 + 淡字**（实测面板中点被渲成 `176,179,255`） |

**修法（两条一起用）：**

1. `alpha = max( max(R,G,B), 主体遮罩 )`。
   主体遮罩 = 外盘＋描边的解析覆盖（`r ≤ 68.6`）—— 该区域内一律 alpha = 1，
   于是**宠物在深浅桌面上颜色完全一致**，深色环、瞳孔不再发白。
2. **自绘 UI 必须单独走真正的 alpha 合成**，不能先 `paste` 进画布再靠 `max(RGB)` 反推：

   ```
   prem_out = 预乘色×(1−a) + UI色×a
   alpha_out = a + alpha_主体×(1−a)
   ```

   所以 `FastMascot.to_bgra(cv, ov=覆盖层)` 才开始收 `ov` 参数，而 `_overlay()` 只**返回**覆盖层、不再往画布上贴。

**顺带一个验收教训**：离线预览图当时是**按黑底 RGB 渲的，完全没验证 alpha**，所以这个 bug 一路溜到了真机。
现在 `step5_preview.py` 改成**按分层窗口的真实规则**合成（`预乘色 + (1−alpha)×桌面色`），
而且**深色桌面和浅色桌面各出一排** —— 这类"只在某种桌面上才现形"的问题才拦得住。

⚠️ 做这个合成时**必须用 int32**：`(255−alpha)×bg` 最大 65025，用 int16 会**溢出成负数**被 clip 成 0，
表现为"挂件周围一圈莫名其妙的黑方块"（踩过）。


### 分项实测（本体 260 px / 画布 422 px）

| 环节 | 耗时 | 备注 |
|---|---|---|
| 抹黑 + 贴底座（全幅） | 0.03 ms | `paste` **不带遮罩 = memcpy** |
| 贴扫描线（全幅，带遮罩） | 0.66 ms | |
| 睫毛遮罩（解析式，219² 裁剪框） | 0.7 ms | **裁剪框尺寸不随画布变** ⇒ 外扩不增加这部分开销 |
| 眼睛 alpha × 眼睑遮罩（161² 裁剪框） | 0.16 ms | 同上 |
| 转 BGRA + alpha（全幅） | 1.85 ms | 见 11.3 |
| **合计** | **≈7.3 ms** | 60fps 预算 16.7 ms 的 44% |

> **画布外扩的代价只落在"全幅"环节**（底座/扫描线/BGRA），裁剪框那几项不受影响。

## 6. 踩过的坑（都已修，记下来防重犯）

### 6.0 ★★ 2026-09-21 晚：主人报"双击启动器没反应" —— 查出**两个 bug**，其中一个会直接崩

#### (a) 单实例锁**静默退出**（"没反应"的直接原因）

`main()` 里原本是：

```python
mutex = kernel32.CreateMutexW(None, False, "FairyPetV2_SINGLETON")
if ctypes.get_last_error() == 183:      # ERROR_ALREADY_EXISTS
    sys.exit(0)                          # ← 没窗口、没提示、连日志都没有
```

**后果**：只要有**任何**残留实例占着这把锁（比如我早先在沙箱里做测试留下的那个），
主人双击启动器 → 新进程撞上锁 → **一声不响地退出**。现场表现就是"我双击了，什么都没发生"，
而且 `pet_error.log` 干净得像什么都没发生过 —— 根本查不到。

**改法（`_poke_existing()` + `tick()` 里的 poke 处理）**：

1. 撞上锁时**不再静默**，而是写 `poke.txt`；
2. 在跑的那个实例每 30 帧检查一次 `poke.txt`，看到就删掉它 → **归位到右下角 + 亮出来**（`_force_show`）→ 冒一句"我在这儿。"；
3. 如果 2.5 秒内poke 没被消费（说明那个持锁的是**卡死/没有窗口的残留实例**），
   **仍然启动新实例**，并把这件事写进 `pet_error.log` —— 宁可两只，也不让主人干等。

实测（隔离环境，互斥名改掉以免碰到真实例）：

| 场景 | 结果 |
|---|---|
| 隐藏启动实例 1，再"双击"一次 | 实例 2 **0.85 秒**返回、退出码 0，输出"已有实例在运行 → 已请它归位并亮出来" |
| `poke.txt` | 被实例 1 消费 ✅（没有残留） |
| 实例 1 | 心跳 `vis=0 → 1`，位置变成归位点，屏幕抓取蓝像素 48749 ⇒ **真的画出来了** ✅ |

#### (b) 换尺寸直接崩（**这才是宠物"突然消失"的原因**）

主人右键点了「尺寸」。`pet_error.log` 抓到：

```
fairy_layers.py:405 in to_bgra
ValueError: operands could not be broadcast together with shapes (520,520,3) (422,422,1)
```

`_switch_size()` 里**漏了 `self.win = self.R.N`**：渲染器已按 320 px 重建（画布 520），
而窗口 / alpha / DIB 还是 260 px 那套（422）⇒ 广播失败 ⇒ 未捕获异常 ⇒ **桌宠整个进程消失**。

**规矩**：换尺寸必须 `px`、`win`、`alpha`、DIB、`SetWindowPos` **五样一起换**。
两层测试：进程内连切 5 次、真窗口下自动切 `260→320→200`，`err` 恒 0、无错误日志、正常退出 ✅。

#### (c) 顺手加固的三处

| 加固 | 原因 |
|---|---|
| 主循环 `tick()` 包 try/except：记日志 + 连续失败计数，**连续 600 帧失败才退出** | 一次渲染异常绝不该让常驻程序整个消失（(b) 的教训） |
| 心跳新增 `pid` / `hwnd` / `vis` / `err` | 否则"进程活着但窗口看不见"外部无从判断 —— 这次就吃了这个亏 |
| 启动时校验 `IsWindowVisible`，不可见就用 `SW_SHOW` 重试并记日志 | 让"窗口没显示出来"这件事**永远留有痕迹** |

#### (d) 一个被**实测证伪**的假设（记下来免得再犯）

我一度把"窗口看不见"归因于 `sh.Run(cmd, 0, False)` 带来的
`STARTUPINFO.wShowWindow = SW_HIDE`（文档说进程首次 `ShowWindow` 会被它覆盖）。
**实测：用 SW_HIDE 启动，`ShowWindow(4)` 照样生效、窗口可见（`vis=1`）** —— 假设不成立。
真凶是 (a)。**没有验证过的因果，就不要写进结论。**

#### (e) 新工具：`check_fairy.vbs`

双击弹窗给出体检结论（在不在跑 / 窗口可见吗 / 在哪 / poke 残留 / 错误日志 / 下一步做什么）。
实现是 `fairy_status.py`，只依赖标准库 + ctypes（不 import numpy/PIL），秒级返回；
报告写成 UTF-16 让 VBS 读成 Unicode 弹窗（避开 ANSI 乱码）。

### 6.1b ★★ 2026-09-21 晚三：辉光最终定稿 =「烟雾感」+「角向厚薄」+「边界游移」

> 本节**取代** 6.1 的部分结论：径向剖面后来不再照抄素材了（原因见下表第 1 行）。

主人的反馈是三轮递进的，每一轮都暴露了我的一处过火：

| 轮 | 主人说 | 量到的根因 | 改法 |
|---|---|---|---|
| 1 | "放大看有一圈比较实的光晕" | ① 我为消缝把 1.00~1.07R **填成峰值** ⇒ 一条 7.7px 的实心亮带；② 动态项**只加不减** ⇒ 亮区顶到 255 | 径向剖面不再照抄素材（素材自带 bloom 亮环，**照抄必有环**），改成合成**单调衰减**；动态改为**双向偏离**（烟能提亮也能压暗） |
| 2 | "白底不规则感不够" | 亮底显示 = 预乘色 + (1−α)×背景 ⇒ 白渗漏把结构冲淡 | 角向不规则 ×1.6；亮底 α 改用**按亮度查表**抬升（单调、不削顶、放大中间调差异） |
| 3 | "边界太均匀，应该有的区域厚有的区域薄" | `GLOW_PROF` 只跟**半径**有关 ⇒ 每个角度的衰减曲线一模一样 ⇒ **外缘是个正圆**。角向图案只改亮度、不改"到哪儿消失" | 把**实测的外缘半径**做成角向**厚薄因子**，直接缩放径向采样半径 |

**第 3 轮的实测依据**（素材 alpha 降到 8/255 处的外缘半径）：
均值 1.913、标准差 0.095、**峰峰 20.3%**；主谐波 k=2（上下薄）4.8% + k=4 3.7%
⇒ **正下方最薄、右下最厚**。低通到 k=1..8 后作为 `glow_thick_table()` 从贴图**现场推导**
（不新增资产、不含手调参数）。

**边界还得会动，而且要"绕圈"而不是"摇"**：第一版我用 `sin` 往复（1.5 s 一摇），
但睫毛是**匀速转** —— 性质不同，看着就不搭（主人的原话："厚薄变动速度跟主体不匹配，
动效应该是让辉光看起来在绕圈，速度不快，但跟瞳孔的变化、尖角绕圈的速度是匹配的"）。
改成**匀速绕圈**，角速度与睫毛完全一致：

| | 角速度 | 转一整圈 |
|---|---|---|
| 睫毛（官方 CSS 15 s/圈） | **24.00°/s** | 15 s |
| 辉光（照抄睫毛） | **24.00°/s** | 15 s |

**架构上要先解决一件事**：辉光相位表原先按**呼吸周期 1.5 s** 预烘 60 帧，
而**匀速旋转不是周期函数**，在 1.5 s 内无法闭合。所以把**辉光自己的相位周期改成 7.5 s**，
并且**不再把形状当成刚体去旋转**，改成"**每个角向谐波各按自己的整数圈数转**"：

```
S(θ, t) = Σ_k |F_k| · cos(kθ + ψ_k − n_k·2π·t/T),      n_k = round(k/2)
```

| 谐波 k | n_k | 视觉角速度 (n_k/k)·48°/s |
|---|---|---|
| **2 / 4 / 6 / 8**（主导） | 1 / 2 / 3 / 4 | 全部 **24.00°/s** —— 与睫毛同速、同向、锁相 |
| 1 / 3 / 5 / 7（很弱） | 1 / 2 / 3 / 4 | 48.0 / 32.0 / 28.8 / 27.4°/s ⇒ **形状持续变形** |

- 每个谐波在 7.5 s 内都转**整数圈** ⇒ 首尾帧逐点重合（是**准周期**，不是真随机）；
- 主导的偶数谐波仍全部 24°/s ⇒ 主人认可的"速度"一点没变；
- 奇数谐波略快 ⇒ **奇偶分量持续错开 ⇒ 形状不再保持镜像对称** ⇒ 这就是"看起来无规律"。

> ⚠️ **别再用"删谐波"来凑闭合**：上一版我为了让"7.5 s 转 180°"对得上，把奇数谐波全删了
> （只留 k=2,4,6,8）—— 那等于**人为把形状做成了 2 重对称**，厚和薄必然呈镜像关系
> （主人一眼看出"太对称"）。**对称性是被"删谐波"毁掉的，不是被"旋转"毁掉的。**
> 正解是让每个谐波**各转各的整数圈**：既闭合，又持续变形。

> 💡 另一个教训：**验证旋转方向不必等 5 分钟重烘** —— 直接对**形状表本身**做相位拟合
> 就能算出角速度与方向（1 秒出结果）。我第一次用 `+i` 做谐波时间相位，方向反了
> （实测 k=2 得到 −24.27°/s，与睫毛的 +23.98 反向），改成 `−i` 才正。
> 数学上 `S(θ,t)=Σ|F_k|cos(kθ+ψ_k+φ_k)` 的特征满足 `dθ/dt = −(1/k)·dφ_k/dt`。

厚度幅度同时 ±30% 起伏（`GLOW_THICK_BREATHE`）。**只移动位置、不抬峰值** ⇒ 不引入削顶。

**动态的"形态"：要"原地游荡"，不要"径向外推"（主人第六轮反馈）**

主人的话："辉光从主体边缘向外扩散的动态效果类似**水波/重力波**（一圈圈同心圆波纹），
而不是那种类似**布朗运动**的无规则运动效果。厚薄和转速都差不多了，动效变化的感觉还差点意思，
应该要更'自由'一点。"

根因（我自己的实现）：

- 每个烟团都沿径向**从 1.02R 单向漂到 1.44R**；
- 外加两道**径向亮环**从 1.02R 扩到 1.46R。

⇒ 两样叠起来就是"一圈圈往外推"，视觉上必然是水波/重力波。

改法：

- 径向改成**零均值来回**（有的向内、有的向外、有的几乎不动）；
- 角向绕自己的基准位置摆动，**幅度与频率各团不同**；
- 强度各有**生灭**（包络随时间起伏）⇒ 不再是"整圈一起明暗"；
- **关掉径向亮环**（`RIPPLE_AMP = 0`）—— 那是最直白的同心圆波纹来源；
- 所有运动由**整数频率的正弦和**合成 ⇒ 一个周期内逐点闭合（准周期，非真随机）。

**验收（怎么证明"不是波"）**：

| 判据 | 结果 | 含义 |
|---|---|---|
| 团的径向位移方向 | 正 50.6% / 负 49.4%；净变化 **0.0000** | 原地游荡，不是漂出去 ✅ |
| **相邻径向带的传播延迟** | 全部 **0 步**（标准差 0.00） | **没有能量沿半径外传** ⇒ 不是波纹 ✅ |

### 6.2 ★ 画布外扩踩的两个坑（都会让 MAE 从 0.5 飙到 3~9）

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 1 | **外扩量没取整到像素** | 宠物中心落在超采样网格的半个像素上 ⇒ 所有裁剪框整体错 1 px。MAE 0.48→9.1，且**误差 85% 集中在宠物内部** | 外扩量 `round(margin_u × ppu)` 取整到最终像素，再乘 ss |

### 6.5 ★★ 2026-09-21 22:4x：工作态改定为**四层** ——「辉光卸下伪装，变成 01 二进制」

**主人的设计意图**（原话）："思考辉光变成 01 状态的一致性，即主体因为进入工作状态而产生的变化，
**卸下了伪装，辉光变成了 01 的二进制符号**。" 另外三条具体要求：数字太密（减 40%）、
数字颜色跟辉光不一样、动效单调（要加摩尔纹 / 淡雾 / 数字背后的光源）。

⇒ 所以工作态**不是**"把辉光换成另一种特效"，而是**同一束光换了形态**。
实现上就是：**四层全部从辉光派生**（同一套配色 / 径向剖面 / 角向厚薄 / 淡雾直接复用辉光相位表）。

| 层 | 名称 | 是什么 | 从辉光派生什么 | 运行时开销 |
|---|---|---|---|---|
| L0 | 底光 `undershine` | 数字背后的**光源**：平滑、低频、非正圆 | 配色 + 角向厚薄基准形状（静态） | 1 次无遮罩 `paste` ≈ 0.01 ms |
| L1 | 淡雾 `mist` | 辉光的**淡残影**（"淡色的雾"） | **直接复用辉光相位表** × `WORK_MIST_K`(0.30) | 1 次带遮罩 `paste` ≈ 0.15 ms |
| L2 | 摩尔纹 `moire` | 角向细纹 × 水平细纹的**干涉**（"辉光那边有这种效果"） | 径向剖面 + 角向厚薄 | 1 次 `lighter` ≈ 0.25 ms |
| L3 | 数字 `digits` | 540 个 0/1 | 亮度包络 + **配色**（见下） | 2.4 ms（260 px） |

**★ 四条被实测逼出来的判断（别退回去）**：

1. **颜色必须取辉光的实测色**。主人说"颜色跟辉光不一样"——根因是写死的 `#c9f8ff` 比例是
   `(0.79, 0.97, 1.0)`（近乎白的青），而辉光实测是 `(0.26, 0.64, 1.0) → (0.10, 0.46, 1.0)`
   （随半径越来越纯蓝）。现在数字按**自己当时的半径**取辉光色（5 档 `COL_RHOS`）：
   `(102,179,255) → (75,143,255)`，同一批数字往外走的过程本身就在变蓝 —— 这就同时给了**层次**。
2. **摩尔纹必须"相加"不是"相乘"**。`cos(f1)·cos(f2)` 的亮部只落在两组同时为峰的交点上
   —— 稀疏亮点，放大看几乎不可见（实测 1.0~1.5R 内均值仅 3.6/255）。
   改用 `0.5 + 0.25·A + 0.25·B`：`cos(f1)+cos(f2) = 2cos(Δf/2)·cos(Σf/2)`
   ⇒ 既留住"看得见的细纹"（基频），又留住拍频（摩尔纹的大块明暗）。**没有同心圆环**
   （主人明确讨厌"水波"）—— 两组都是"角向放射 + 水平横纹"。
3. **`lighter`（取 max）叠加 ⇒ 图案的暗部无效**，实际对比度只有幅度的一半；
   而且每层必须**比它下面那层更亮**才浮得出来（摩尔纹峰值 69 > 同半径底光 50）。
   一开始按"正常 alpha 合成"的直觉给 0.10，结果等于没有。
4. **★ 尺度陷阱（真 bug，MAE 从 1.7 飙到 8.5）**：`fairy_layers` 里
   `_u8(a)` 期望 **0..1**（内部 ×255），而 `_u8rgb(a)` 期望 **0..255**。
   `work_mist_alpha()` 返回的是 alpha 尺度（0..255），直接喂给 `_u8` 会被整片 clip 成 255
   ⇒ 雾变成"辉光整幅贴上"，工作态亮得跟常态一样。**必须 `/255`**。加新图层时先确认这个。

**其它同步改动**：`N_DIGITS` 900 → **540**（−40%）；`OPACITY_PEAK` 0.90 → **0.86**
（辉光峰值就是 180，数字不该比它还亮，否则放大看是"白字"而不是"光变的字"）；
`BLUR_U` 0.62 → **0.68**；底光/雾补上后"密度降低导致的空"由那两层填。

**实测数值**（本体 260 px，暗底 #1B1D23）：

|---|---|---|---|---|
| L0 底光 | 85 | 40.2 | **0** | 0 |
| L1 淡雾 | 53 | 19.8 | **0** | 0 |
| L2 摩尔纹 | 69 | 11.2 | **0** | 0 |
| L3 数字 | 207 | 19.5 | **0** | 0 |
| 四层叠加 | 207 | — | **0** | **0** |

15 s 首尾差 **0**（底光静态、摩尔纹 7.5 s 整数圈、数字 15 s 整数趟、雾随辉光 7.5 s 周期）
⇒ **视频能无缝循环**。

**★ 2026-09-22 改定：数字"显现范围"的厚薄 —— 与辉光同量级 + 少量逸散出辉光边界。**
主人三轮反馈把这一项定了下来：
① "数字显现的范围（跟辉光的厚薄同理）变化不太大" ⇒ 实测数字可见外缘峰峰 **18.3%** vs 辉光 **30.2%**；
② "可以比辉光的变动幅度更大些，因为是一些数字逸散效果" ⇒ 加到 38.2%；
③ "**又有些过于夸张了**……其实应该是**部分数字**的厚度超出辉光厚度，估计 **30% 左右**吧，
其余部分还是最大幅度保持跟辉光的幅度基本一致；而且这次数字怎么看起来大了不少，
**上一版数字的大小我觉得挺好**。"

最终方案 = **非对称行程缩放 + 亮度/字号解耦**：

| 杠杆 | 现值 | 作用 |
|---|---|---|
| `DIG_AMP_POS` | 1.00 | 厚端方向的**行程**缩放（顶到画布允许的极限） |
| `DIG_AMP_NEG` | 0.32 | 薄端方向的**行程**缩放（只收一点） |
| 亮度曲线 | `GLOW_PROF`（**辉光那条**，按**行程半径** `rho0` 查） | 末端严格归零；不牵动字号 |
| 字号 | 另用 `sz_ref = GLOW_PROF(rho0)` 独立算 | **与亮度解耦**（见下面的教训 ②） |
| `DIG_RHO_CAP` | 1.58 | 位置硬上限（画布半宽 1.66R 减半个字） |
| `DIG_FADE_R0/R1` | 1.56 / 1.70 | 兜底收口（防硬上限处堆成一道"墙"） |

**四条被实测打回来的做法**（都留作教训）：

1. **亮度按"缩放后的位置"查表** ⇒ 推远的那段又被按远处压暗 ⇒ 等于白推（可见外缘起伏只剩 7.7%）。
   必须按**行程半径** `rho0` 查。
2. **为了让"逸散"可见而另做一条更长的亮度剖面** ⇒ 推出去的数字确实亮了，但

   正解是**解耦**：亮度一条、字号另用 `sz_ref` 一条。
3. **淡出收口的起点必须晚于目标逸散半径**。先把它设在 1.44R（= 辉光边界）⇒ 逸散刚出门就被吃掉，
   实测 **0/72 个方向**能突破。
4. **画布是硬上限**：位置最远只能到 ≈1.58R（半宽 1.66R 减半个字）。所以"凑出 30% 的起伏"
   只能靠**非对称**缩放 —— 厚端顶到上限、薄端让一点。对称缩放怎么调都摆不平。

⇒ **均值与峰峰都和辉光对齐**（1.29 vs 1.28、30.0% vs 30.2%），

### 6.6 右键菜单改成滑块式（2026-09-22，主人指定）

要求：尺寸行加**三档滑块**（小/中/大，右侧带实际像素）；自动/手动也做成滑块；
切到**手动**时下方**多一行**「状态」（常态/工作态），切到**自动**时下方**多一行**「自动」
（跟随 WorkBuddy / 60 秒循环）。滑块要能**点**也能**按住拖**。

六条实现要点（旧版是"固定项列表 + 等分行高"，这套在滑块下全都不成立）：

1. **行数随模式变** ⇒ 菜单必须**每帧动态算布局**（`_menu_rows()` / `_menu_layout()`），
   不能再靠一个写死的 `MENU_ITEMS`。
2. **段宽按字体实测宽度给**（`ImageDraw.textlength`）—— 固定宽度一改文案或换字体就溢出。
3. **菜单宽度按"两种模式里更宽的那一行"算死** ⇒ 切自动/手动时不会横向跳
   （否则"跟随 WorkBuddy"那一行会让菜单忽宽忽窄）。
4. **拖动必须 `SetCapture`**：不设 capture 的话指针一移出窗口就收不到 `WM_MOUSEMOVE`，
   拖到一半就断（窗口拖动原本就有 capture，滑块是新加的一处）。
5. **段间那 2 px 缝隙的命中算进左段** ⇒ 按住拖过缝隙不会"失灵一下"。
6. **每一档必须幂等**：拖动会**反复**触发同一个分段（`_set_slider` 里每档都要判"值没变就啥也不做"），
   否则每帧都会重放一次气泡/切换动作。

**顺带一个坑**：`_overlay()` 返回的 PIL 数据**实际是 BGR 序**（它要交给 `to_bgra(ov=...)` 当 BGR 用）。
预览脚本里直接 `.convert("RGB")` 会红蓝对调 —— 蓝色滑块会显示成**橙色**
（这次就是这么被自己抓到的：菜单真机是蓝的，预览图是橙的）。
预览时必须 `Image.merge("RGB", im.split()[::-1])` 翻回来。
